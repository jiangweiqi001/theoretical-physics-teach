# Theoretical Physics Teach v0.4.0 Quality Upgrade Design

**Date:** 2026-08-11

**Project:** `theoretical-physics-teach`

**Release target:** `v0.4.0`
**Status:** Approved for implementation

## 1. Purpose

`v0.4.0` is a structural quality release. It does not add a new teaching mission and does not replace the course model delivered in `v0.3.0`. It makes that model easier for an Agent to execute, easier for a theoretical-physics learner to understand, easier for a maintainer to verify, and safer to publish.

The release preserves these behaviors:

- resume at the exact first unfinished equation, proof step, code operation, or conceptual obstacle;
- integrate substantive chat clarification into the first dependent location in the active Note;
- rewrite both surrounding transitions and repair notation, numbering, provenance, links, and the final checkpoint so the complete Note remains continuous;
- use Obsidian-compatible `.md` only, with `$...$` inline mathematics and `$$...$$` display mathematics;
- preserve source-local notation and express cross-source translations through canonical crosswalk and synthesis records;
- default diagnosis and ordinary checks to one multiple-choice or true/false item at a time, while requiring produced work for reconstruction capability;
- activate the code-theory bridge only when implementation is a mission target and trustworthy corresponding material is available.

The design must not overwrite, delete, or bulk-migrate any user learning workspace. Existing `v0.3.0` lesson-local Code Maps remain valid.

## 2. Audit findings

The `v0.3.0` baseline passes every shipped contract and validator test. The quality audit nevertheless found five maintainability and publication weaknesses.

### 2.1 The lesson template mixes core teaching with optional infrastructure

`assets/templates/LESSON.md` is 482 lines. Approximately 265 lines describe optional Code Map and Run registry protocols. A theory-only lesson therefore carries more code-infrastructure schema than learner-facing physics structure.

This weakens progressive disclosure and makes it harder for an Agent to distinguish ordinary lesson requirements from the conditional code path.

### 2.2 Behavioral fixtures are not a complete normative example

The accepted GREEN outputs are useful historical behavioral snapshots, but the current contract checks mostly sentinel phrases, first heading, delimiters, and selected facts. They are not a concise public example and do not prove the complete workspace lifecycle or every notation dependency.

### 2.3 Public onboarding is complete but difficult to scan

The English README explains the project thoroughly, but it lacks compact navigation, a five-minute path from installation to first durable Note, a full resume/writeback walkthrough, and an equally complete Chinese entry point.

### 2.4 Codex metadata is missing a default prompt

`agents/openai.yaml` correctly disables implicit invocation but does not provide a short `interface.default_prompt` that explicitly demonstrates `$theoretical-physics-teach`.

### 2.5 CI and release packaging do not demonstrate portability or a clean runtime payload

Validation runs only on Windows. Workflow actions use movable major tags from older releases. The GitHub release has source archives but no intentionally assembled runtime-only Skill package.

## 3. Chosen approach

Use a balanced structural upgrade. Do not rewrite the course architecture.

The alternatives rejected are:

- **documentation-only polish:** too small because it leaves the oversized conditional template and weak package boundary unchanged;
- **full workspace rewrite:** too risky because it could invalidate existing Notes, Code Map identities, evidence links, or resume state.

The chosen approach separates optional schemas, adds one normative end-to-end example, strengthens deterministic validation, improves public documentation, hardens CI, and publishes a clean package while preserving `v0.3.0` workspace compatibility.

## 4. Runtime architecture

### 4.1 Core lesson template

`assets/templates/LESSON.md` remains the template for `lessons/{lesson-id}-{slug}.md`. It continues to own:

- the mandatory first H2 `## Notation and conventions`;
- complete before-first-use local symbol definitions;
- mission connection, prerequisites, and Note navigation;
- exact source anchors and provenance;
- one physical question;
- complete derivation or proof;
- physical interpretation and checks;
- conditional cross-source comparison;
- learner-facing exercises, mastery links, and final checkpoint;
- a concise conditional code-theory bridge section.

The concise code section retains only learner-facing information:

- gate state: `Active`, `Blocked`, or `N/A`;
- immutable source or implementation anchor status;
- links to canonical Code Maps and Run records;
- theory object and source equation;
- physical-quantity derivation chain;
- equation-to-variable mapping;
- algorithm or pseudocode explanation;
- inputs, outputs, validation observable, and explicit non-claims.

It does not embed registry allocation protocols or full Code Map and Run schemas.

### 4.2 Code Map template

Add `assets/templates/CODE-MAP.md` as the only new canonical template for newly created shared or lesson-scoped Code Map files under `reference/code-maps/`.

The template owns:

- append-only Code Map identity and lifecycle fields;
- architecture-level mapping;
- physical-quantity derivation chains;
- line- or operation-level mappings;
- theory anchors, implementation anchors, assumptions, discretization, units, domains, shapes, indices, inputs, outputs, and non-claims;
- references to immutable Run records when execution evidence exists.

New Code Maps are external Note files linked by lessons. Existing Code Maps already embedded in `v0.3.0` lessons remain valid and are never migrated automatically.

### 4.3 Run record template

Add `assets/templates/RUN-RECORD.md` for immutable `execution-records/RUN-*.md` instances.

The template owns:

- append-only Run identity and lifecycle;
- exact command, working directory, environment, dependencies, hardware, seed, precision, and tolerances;
- immutable code revision or snapshot anchor;
- inputs, raw output artifacts, hashes, convergence diagnostics, validation observables, discrepancies, uncertainty, and non-claims;
- observed and computed execution-evidence items.

Lessons and Code Maps link Run IDs; they do not copy Run payloads.

### 4.4 Skill routing

`SKILL.md` remains the always-loaded core. It keeps the behavioral invariants and explicit gate logic, but delegates optional Code Map and Run schema details to `references/code-theory-bridge.md` and the two new templates.

`references/code-theory-bridge.md` is loaded only when the code gate is `Active`, or when implementation is required but blocked. It explains how to instantiate and link the new templates.

The `SKILL.md` body should remain below the Agent Skills recommended 5,000-token boundary. The release must measure and report its word and line counts.

## 5. Compatibility

### 5.1 Learning workspaces

The release must never overwrite existing workspace files during bootstrap or resume. It must accept:

- `v0.3.0` lessons containing lesson-local Code Map schemas;
- `v0.4.0` lessons linking external Code Maps;
- a mixed workspace containing both forms.

Only newly allocated Code Maps and Runs use the new templates. There is no automatic migration command in `v0.4.0`.

### 5.2 Installed Skill

The installed Skill directory remains `theoretical-physics-teach`, and explicit invocation remains `$theoretical-physics-teach`.

The user learning workspace remains external to the installed directory. Updating the installed Skill must not touch course Notes.

## 6. Normative example

Add one small, self-contained example workspace under `examples/retarded-propagator/`. It is documentation and a validation fixture, not a source of real learner evidence.

The example demonstrates one continuous learning event:

1. a registered illustrative source excerpt supplies the free retarded propagator convention;
2. a baseline option question locates the learner boundary;
3. the lesson reaches the regulated Fourier transform;
4. the learner reports that the reduction from the full time integral to the positive-time integral is unclear;
5. the clarification is integrated at the first dependent step rather than appended;
6. the transition into and out of the explanation is rewritten;
7. leading notation is complete before every symbol's first use;
8. `CURRENT-STATE.md` records the exact completed boundary, remaining obstacle, deep link, and one next action;
9. the final checkpoint uses one option item and does not claim reconstruction mastery from recognition alone.

The example uses explicitly illustrative source IDs and anchors. It must not claim to be a canonical learner workspace or evidence from a real paper.

The example must pass the same read-only workspace validator used for real workspaces.

## 7. Documentation

### 7.1 English README

Restructure `README.md` without weakening its current identity, audience, feature, comparison, legal, or limitation statements. Add:

- top-level English/Chinese navigation;
- a compact table of contents;
- a five-minute install-and-first-session path;
- a minimal explicit invocation prompt;
- links to the complete walkthrough and architecture document;
- a clear distinction between cloning the development repository and installing the runtime-only release package;
- `v0.3.0` to `v0.4.0` compatibility notes;
- current validation and release-package commands.

### 7.2 Chinese README

Add `README.zh-CN.md` with equivalent substance, not a one-paragraph summary. It must explain:

- intended theoretical-physics audience;
- exact resume and coherent writeback;
- notation-first and cross-source behavior;
- Obsidian and LaTeX constraints;
- option-first assessment with reconstruction safeguards;
- conditional code-theory bridge;
- installation, invocation, upgrade, validation, limitations, license, and attribution.

### 7.3 Architecture and walkthrough

Add:

- `docs/architecture.md`: canonical owners, state transitions, source/notation/evidence/code relationships, compatibility boundary, and progressive-loading map;
- `docs/walkthrough.md`: a readable guide through the normative example, including the before/after writeback point and exact next-session resume behavior;
- `CHANGELOG.md`: release history for `v0.1.0` through `v0.4.0`, with a detailed `v0.4.0` compatibility section.

Historical design and implementation records under `docs/superpowers/` remain in Git history and the repository. They are not runtime instructions and are not copied into the runtime-only package.

## 8. Validation design

### 8.1 Static package contract

Extend the static contract so it fails before production changes and requires:

- `CODE-MAP.md` and `RUN-RECORD.md`;
- a compact `LESSON.md` that links external Code Maps and Runs but contains no registry bootstrap schema;
- the explicit Codex `default_prompt`;
- English and Chinese README files, architecture, walkthrough, changelog, and example workspace;
- no forbidden HTML, CSS, JavaScript, browser-dependent lesson, or forbidden math delimiter in production instructions, templates, docs examples, or example workspace.

### 8.2 Workspace validator

Extend `scripts/validate_workspace.py` test-first. For canonical files under `lessons/`, it must report:

- the first H2 is not exactly `## Notation and conventions`;
- the final H2 is not exactly `## End-of-Note checkpoint`;
- existing link, duplicate block ID, delimiter, code-fenced mathematics, and non-Markdown artifact errors.

Do not attempt a general symbolic-mathematics parser in this release. Recursive notation completeness remains a behavioral and example-review contract because a naive regex would create false confidence.

### 8.3 Example contract

Add a deterministic example contract that verifies:

- every required example file exists;
- all example Note links resolve through the workspace validator;
- the active lesson has exact first and final H2 headings;
- `CURRENT-STATE.md` contains a deep link to the exact resume block, a specific obstacle, and one next action;
- the clarification appears at the first dependent derivation step and the Note contains no detached transcript or clarification appendix;
- no live Run or Code Map claim exists when the example code gate is `N/A`;
- every illustrative status is visibly labeled as example/demo data.

### 8.4 Documentation link contract

Add a small standard-library Python checker for relative Markdown links in `README.md`, `README.zh-CN.md`, `CHANGELOG.md`, and current public docs. External URLs are listed but not fetched during deterministic CI.

### 8.5 Behavioral snapshots

Retain existing scenarios, baseline outputs, and GREEN outputs as historical regression material. Document that they are behavioral snapshots, not the normative public workspace example. Do not silently promote their limited phrase contract into proof of complete Note quality.

## 9. Codex metadata

Keep:

```yaml
policy:
  allow_implicit_invocation: false
```

Add a quoted, one-sentence `interface.default_prompt` that includes the exact `$theoretical-physics-teach` invocation and asks to use supplied sources in an external learning workspace.

Keep all YAML strings quoted.

## 10. CI and supply-chain hardening

The validation workflow must:

- run on both `windows-latest` and `ubuntu-latest` through a matrix;
- use PowerShell Core for cross-platform contract scripts;
- use Python 3.12 for validator and package tests;
- pin GitHub-maintained actions to verified full commit SHAs with the release tag documented in an inline comment;
- use least-privilege `contents: read` permissions;
- run static, bootstrap, scenario, GREEN snapshot, example, documentation-link, workspace-validator, and package tests;
- build the runtime package in CI without publishing from pull requests.

Add `.github/dependabot.yml` for weekly `github-actions` version updates so pinned SHAs remain maintainable.

## 11. Runtime-only package

Add a deterministic standard-library Python packager. Given the repository root and an output path, it creates a ZIP containing exactly:

- `SKILL.md`;
- `agents/`;
- `assets/`;
- `references/`;
- `scripts/validate_workspace.py`;
- `README.md` and `README.zh-CN.md`;
- `LICENSE` and `NOTICE.md`.

The package excludes:

- `.git/` and GitHub workflow configuration;
- `tests/`;
- `docs/superpowers/` and other development plans;
- the normative example workspace;
- caches, bytecode, temporary files, and prior archives.

The package test must extract the archive to a temporary directory, compare its manifest against the allowlist, run Skill validation on the extracted root, and run the installed workspace validator unit smoke case.

The final `v0.4.0` GitHub release receives the generated ZIP as a release asset. Source archives remain available automatically.

## 12. Release and installation

After local verification:

1. review the full branch diff against this design;
2. run every contract and unit test from a clean checkout;
3. push the feature branch and create a pull request;
4. wait for both Windows and Ubuntu CI jobs;
5. merge only after the checks succeed;
6. tag the merged commit `v0.4.0` and publish release notes plus the runtime ZIP;
7. update the installed copy at `C:\Users\25739\.agents\skills\theoretical-physics-teach` without bulk deletion;
8. compare the installed runtime manifest and file hashes with the release package;
9. run Skill validation and a workspace-validator smoke test from the installed copy.

No course workspace file is part of installation or upgrade.

## 13. Acceptance criteria

The release is acceptable only when all of the following are demonstrated with fresh command output:

- the new templates exist and the ordinary lesson template no longer embeds Code Map or Run registry bootstrap schemas;
- the core teaching, exact-resume, coherent-writeback, notation, assessment, provenance, and code-gate contracts remain present;
- existing contracts and validator tests still pass;
- new validator tests are observed failing before implementation and passing afterward;
- the normative example passes all structural checks and a manual continuity/notation audit;
- English and Chinese documentation have no broken relative links and contain the exact current invocation and repository identity;
- the extracted runtime package has only allowlisted files and passes Skill validation;
- Windows and Ubuntu GitHub Actions jobs succeed on the merged release commit;
- the GitHub release contains the runtime ZIP;
- the locally installed Skill matches the release payload and validates successfully;
- the repository, release, and installed Skill remain theoretical-physics-only and contain no repository-star promotion.
